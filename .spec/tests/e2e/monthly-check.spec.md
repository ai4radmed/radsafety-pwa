# 테스트 명세: 월간 수동 점검 위저드 (E2E)

## 대상 구현체

- 경로: 프로덕션 배포 전체 (https://radsafety.kr) — 자동 모니터(아침 헬스체크)가 원리적으로 못 덮는 **부작용 있는 실사용 경로**를 사람 동석 하에 반자동으로 검증
- 관련: `documents/test_strategy.md` 4장 수동 체크리스트, `.github/workflows/monthly-reminder.yml` (월간 리마인더)

## 배경 (왜 존재하는가)

아침 헬스체크(Doctor·스모크)는 **부작용 0** 원칙이라 "실제로 보내고 받는" 경로 — OTP 메일 수신, 카카오 OAuth, 푸시 실수신, 파일 실다운로드, Resend 실발송 — 를 검증하지 못한다. 이 위저드는 그 사각지대를 **사람이 필요한 순간에만 개입**(코드 입력 1회·클릭 2회·휴대폰 확인 1회)하고 나머지 판정은 전부 자동화하여, 순수 수동 15~20분 루틴을 약 3분으로 압축한다.

역할 분리: 무인 감시 = 아침 헬스체크(부작용 0) / 부작용 있는 실사용 점검 = 이 위저드(사람 동석, 로컬 수동 발화 전용). **CI·cron 에 절대 올리지 않는다.**

## 테스트 도구

Playwright (E2E) — chromium, headed (사람 개입 필요)

## 실행 조건 (게이트)

- **`TEST_MONTHLY=true` 인 경우에만 실행.** playwright.config 이 `monthly-check` 단일 프로젝트로 동작: dev 웹서버를 띄우지 않고 baseURL 을 `MONTHLY_BASE_URL`(기본 `https://radsafety.kr`)로 잡는다.
- 평상시 CI e2e·로컬 `npm run test:e2e` 에서는 chromium 프로젝트 `testIgnore` 로 제외.
- 실행: `npm run check:monthly` (선택: `MONTHLY_EMAIL=me@example.com npm run check:monthly` 로 이메일 입력 자동화)
- 테스트 전체 타임아웃 30분(사람 대기 포함), 단계별 사람 대기 5분.

## 검증 항목 (단계 순서 고정 — ①의 세션을 ②③④가 사용)

| 단계                   | 검증 내용                                            | 사람 개입                                               | 자동 판정                                                                                                          |
| ---------------------- | ---------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| ① 이메일 OTP 로그인    | Supabase Auth 메일 발송 → 실수신 → 세션 생성 전 구간 | 6자리 코드 입력 (MONTHLY_EMAIL 미설정 시 이메일 입력도) | `/mypage` 도달. `#otpSentTo` 문안에서 로그인 이메일 캡처(④에서 사용)                                               |
| ② 자료실 파일 다운로드 | Storage 실파일 서빙                                  | 없음                                                    | 첫 자료 카드 클릭 → 팝업(slug 형) 또는 모달 `#downloadLink`(구형)에서 파일 URL 획득 → HTTP 200 + 본문 1KB 초과     |
| ③ 의견 보내기          | `sendFeedback` 액션 + Resend 실발송                  | 없음 (수신은 메일함에서 겸사 확인)                      | `[월간점검]` 제목으로 제출 → confirm 자동 수락 → 성공 alert 문안에 '실패' 미포함                                   |
| ④ 푸시 발송·실수신     | 알림 생성 + 웹 푸시 프로덕션 경로 (액션→VAPID→구독)  | 휴대폰 알림 확인 후 브라우저 버튼 클릭                  | 관리자 알림 발송 화면에서 **특정 사용자 = 본인** 선택 → 발송 성공 alert(✅) → 사람이 [도착함/안 옴/구독 없음] 선택 |
| ⑤ 카카오 로그인        | 카카오 OAuth + `/auth/callback` 전 구간              | 카카오 버튼 클릭(및 필요 시 카카오 로그인)              | 새 컨텍스트(비로그인)에서 `/mypage` 도달                                                                           |
| 종합                   | 전 단계 결과 요약                                    | 없음                                                    | 결과 표 출력, FAIL 1건 이상이면 테스트 실패                                                                        |

## 핵심 규칙

1. **부작용은 전부 본인·개발자 한정** — 푸시·알림은 실행자 자신에게만, 의견 이메일은 `[월간점검]` 접두어 + 관리자 발신 조건으로 `DEVELOPER_EMAILS`(서버 env)에만 라우팅된다(`resolveFeedbackRecipients`, 명세 `.spec/src/config/auth.md` 규칙 4 — 관리자 전원 발송 사고 재발 방지). 반복 실행 안전. 자료 조회수 +1 은 실사용과 동일하므로 허용.
2. **자격증명 비저장** — 이메일 코드·카카오 로그인은 사람이 그 자리에서 입력. 세션 파일도 저장하지 않는다(기존 `session-*.json` 을 덮어쓰지 않음). 로컬 `.env`·비밀키 불요.
3. 단계 실패 시 중단하지 않고 **끝까지 진행** 후 요약에서 일괄 판정. ① 실패(로그인 불가) 시 ②③④는 SKIP.
4. ④에서 관리자가 아닌 계정이면 SKIP (권한 alert 감지). 푸시 구독이 없으면 사람이 [구독 없음] 선택 → SKIP.
5. 사이트의 `confirm`/`alert` 는 자동 수락하되 문안을 수집해 성공/실패 판정에 사용한다.
