# 명세: src/actions/index.ts

## 역할 요약

Astro server actions 진입점. `defineAction`으로 `saveFinding`, `deleteFinding`, `sendVerificationCode`, `verifyEmailCode`, `sendNotification`, `sendFeedback`, `signUpWithUsername`, `signInWithUsername`, `claimUsername`, `approvePendingMember`, `rejectPendingMember`를 export한다. Supabase, 이메일, 푸시, 로거를 사용한다.

## Public API (server 객체)

| 액션                   | input                                                                                                                  | 설명                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `saveFinding`          | id?, title, findingType, tags, year, description, violationClause?, solution?                                          | findings 테이블 insert/update. `id`가 `local-`로 시작하면 insert                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `deleteFinding`        | id                                                                                                                     | findings 삭제. `local-` id는 무시                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `sendVerificationCode` | email, userId                                                                                                          | 6자리 코드 생성, DB 저장, 이메일 발송                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `verifyEmailCode`      | code(6자), userId                                                                                                      | 코드 검증 후 verified 업데이트                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `sendNotification`     | senderId, targetType, provider?, verificationStatus?, specificUserId?, title, message, link?, actionLabel?, actionUrl? | 관리자만. profiles 조회 후 notifications insert, 웹 푸시 발송                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `sendFeedback`         | userId?, userName, userEmail, title, message, attachments?                                                             | feedback insert, 관리자 이메일 발송                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `approveVerification`  | adminId, targetUserId                                                                                                  | 관리자 권한 확인 후 타겟 사용자 인증 승인 (verified)                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `rejectVerification`   | adminId, targetUserId, reason                                                                                          | 관리자 권한 확인 후 타겟 사용자 인증 반려 (rejected)                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `revokeVerification`   | adminId, targetUserId                                                                                                  | 관리자 권한 확인 후 타겟 사용자 인증 회수 (temp_verified)                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `signUpWithUsername`   | username, password(8자+), hospitalId?, society?                                                                        | Stage 1-A + Phase 2. `profiles.username` 중복확인 → `auth.admin.createUser`(가짜 이메일 `<username>@radsafety.invalid`, `email_confirm:true`) → `profiles` **upsert**(`onConflict: 'id'`, insert 아님 — 이유는 규칙 10), **`status: 'pending'`**·`hospital_id`·`society` 포함(규칙 11). profiles upsert 실패 시 방금 만든 auth 계정 롤백(삭제). 반환 `{success, email}` — 클라이언트가 그 email 로 `signInWithPassword` 를 이어서 호출                                                                                 |
| `signInWithUsername`   | username                                                                                                               | `profiles.username` → id → `auth.admin.getUserById` 로 email 조회만. 비밀번호 검증은 하지 않음(클라이언트가 반환된 email 로 `signInWithPassword` 호출). 아이디 없음/조회 실패 모두 같은 문구(`아이디 또는 비밀번호가 올바르지 않습니다.`)로 응답해 아이디 존재 여부 비노출                                                                                                                                                                                                                                             |
| `claimUsername`        | userId(uuid), username, password?(8자+), hospitalId?, society?                                                         | Stage B(전환기간) + Phase 2. 다른 사용자가 쓰는 아이디면 에러(본인 재확정은 허용). `auth.admin.updateUserById`로 email 을 가짜 이메일로 교체(password 주어지면 같이 설정) + `profiles.username/login_email(NULL)/nickname(NULL)` 갱신. `hospitalId`/`society`는 **필드가 아예 안 왔으면(undefined) 갱신 안 함** — 기존 active 계정의 평범한 전환(신규 필드 안 보임)에서 소속기관을 실수로 지우지 않기 위해(규칙 11). password 는 서버에서 optional — 강제 여부(카카오 선택/이메일 출신 사실상 필수)는 클라이언트 UI 몫 |
| `approvePendingMember` | adminId, targetUserId                                                                                                  | Phase 3. 관리자 권한 확인 후 대상 계정 `profiles.status`를 `pending`→`active`로 변경                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `rejectPendingMember`  | adminId, targetUserId                                                                                                  | Phase 3. 관리자 권한 확인 후 대상 계정 `profiles.status`를 `banned`로 변경(규칙 12) — 재가입은 새 계정으로                                                                                                                                                                                                                                                                                                                                                                                                             |

## 사이드 이펙트

- DB: findings, email_verification_codes, profiles, notifications, feedback
- Supabase Admin Auth API: `auth.admin.createUser`/`getUserById`/`updateUserById`/`deleteUser` (signUpWithUsername/signInWithUsername/claimUsername)
- 이메일: sendVerificationEmail, sendFeedbackEmail
- 푸시: sendPushToUsers
- 로거: createLogger('actions')

## 핵심 규칙

1. `accept: 'form'`은 saveFinding만 사용.
2. sendVerificationCode: 코드 유효 10분, profiles에서 사용자 이름을 조회하여 이메일 개인화. 이메일 발송 실패 시 에러 처리.
3. sendNotification: targetType별 profiles 필터(all/provider/verification_status/specific).
4. sendFeedback: 이메일 실패해도 DB 저장 성공 시 성공 처리.
5. sendFeedback 수신자: `resolveFeedbackRecipients(title, userEmail, DEVELOPER_EMAILS)` 로 결정. `DEVELOPER_EMAILS` 는 서버 전용 env(쉼표 구분, PUBLIC 아님)를 모듈 로드 시 파싱 — 테스트성 의견(`[월간점검]` + 관리자 발신)만 개발자 목록으로 라우팅되고, 미설정 시 종전대로 관리자 전원.
6. `usernameSchema`(모듈 내부): trim → 소문자화 → `^[a-z0-9_-]{3,20}$` 검증. 세 액션 공통 사용 — DB 에는 항상 소문자만 저장된다(대소문자 구분 없는 로그인은 저장 시 정규화로 구현, DB 단 citext/대소문자무시 인덱스는 쓰지 않음).
7. 가짜 이메일은 `<username>@radsafety.invalid` 로 결정적으로 파생(모듈 내부 `fakeEmailFor`) — RFC 2606 예약 도메인이라 실제 메일 발송·등록 불가.
8. **세션 쿠키는 이 세 액션이 직접 설정하지 않는다.** `context`(cookies/request)를 쓰지 않고 email 만 반환 — 기존 개발자 테스트 로그인(`login.astro`)과 동일하게 **클라이언트의 브라우저 supabase 클라이언트가 `signInWithPassword` 를 호출**해 세션을 연다. 이 코드베이스의 다른 액션들도 context 를 쓰지 않는 관례(테스트 모의 `tests/mocks/astro-actions.ts` 도 context 인자를 지원하지 않음)를 따른 것.
9. `claimUsername` 은 세션이 아니라 클라이언트가 넘긴 `userId` 를 그대로 신뢰한다 — `approveVerification`/`sendNotification` 등 기존 관리자 액션과 같은 관례(명시적 id 전달, context 기반 아님).
10. `signUpWithUsername`의 profiles 쓰기는 **반드시 `upsert(onConflict:'id')`** — 운영 Supabase 에 `auth.users` insert 시 `profiles` 에 빈 행을 자동 생성하는 DB 트리거가 있다(2026-09-16 프리뷰 실측: 새 아이디마다 재현되는 `duplicate key value violates unique constraint "profiles_pkey"` 로 발견, 어떤 username 을 써도 동일하게 재현돼 특정 값이 아닌 트리거 문제로 확정). 평범한 `insert` 로 되돌리면 가입이 항상 실패한다. 트리거 자체는 이 저장소의 `sql_query/*.sql` 에 없다(대시보드에서만 존재하는 것으로 추정) — 정확한 정의는 Supabase SQL Editor `select pg_get_triggerdef(oid) from pg_trigger where tgrelid = 'auth.users'::regclass;` 로 확인 가능.
11. **Phase 2(2계층+가입승인+제재 모델, KSNM 방안위 교육팀 합의 2026-09-10 승계)**: `hospitalIdSchema`(모듈 내부)는 빈 문자열을 `null`로 변환하고, 그 외 값은 `src/data/hospitals.ts`의 `HOSPITALS`에 실제로 존재하는 `id`인지 검증 — `HospitalAutocomplete.astro`가 목록 클릭으로만 값을 채우므로, 알 수 없는 id 가 오면(UI 우회 등) 조용히 버리지 않고 명확히 거부한다. `societySchema`는 `'nuclear_medicine' | 'technology' | 'none'` 이넘. 둘 다 선택 항목(`documents/privacy_redesign_plan.md` §2-2). `signUpWithUsername`은 신규 계정에 항상 `status: 'pending'`을 명시(관리자 승인 전까지 회원 계층 기능 접근 불가 — 접근 제한 자체는 Phase 4/5에서 구현). `claimUsername`은 `status`를 건드리지 않는다(자가치유로 막 생긴 pending 계정이든, 기존 active 계정이든 이미 정해진 값을 그대로 둔다).
12. **Phase 3(가입 승인 화면, `src/pages/admin/member-approval.astro`)**: `approvePendingMember`/`rejectPendingMember`는 `approveVerification` 등 기존 관리자 액션과 동일한 관례로 `adminId`를 클라이언트가 넘기고 서버가 `profiles.is_admin`을 대조한다(세션 기반 아님). 거절은 `status: 'banned'`로 처리 — CHECK 제약(`pending`/`active`/`suspended`/`banned`)에 "가입 거절" 전용 값이 없어 기존 값을 재사용한 것으로, 봉인된 계정을 다시 열어주는 절차는 없고 재가입은 새 username으로 한다.
