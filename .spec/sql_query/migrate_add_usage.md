# migrate_add_usage.sql — 사용성 집계 테이블

## 왜

v1.0.0 으로 기능은 다 들어갔는데 **무엇이 실제로 쓰이는지 알 방법이 없다.** 다음에 무엇을 만들지, 어디에서 이용자가 포기하는지 정하려면 근거가 필요하다(Dr. Ben 2026-09-20, `documents/privacy_redesign_plan.md` U 트랙).

제3자 분석 도구(GA4·PostHog·Umami 등)는 쓰지 않는다 — 쿠키·IP·해외 전송이 따라와 처리방침과 충돌하고, 수백 명 규모에 그 기능이 필요하지도 않다. 필요한 최소치만 직접 센다.

## 테이블

| 테이블         | 보존                              | 용도                           |
| -------------- | --------------------------------- | ------------------------------ |
| `usage_events` | `USAGE_RETENTION_DAYS`(기본 35일) | 원시 이벤트 1건 = 1행          |
| `usage_daily`  | 영구                              | 일자·이벤트별 횟수와 활성자 수 |
| `usage_active` | 영구                              | 일·주·월 활성 사용자 수        |

`usage_daily`·`usage_active` 는 U-4 의 야간 롤업이 채운다. U-1 은 `usage_events` 만 쓴다.

## 익명화

회원 식별자를 그대로 저장하지 않는다. `USAGE_HMAC_SECRET` 으로 기간과 섞은 되돌릴 수 없는 값만 남긴다.

- `actor_key` = HMAC(비밀키, `d:<회원식별자>:<KST 날짜>`)
- `week_key` = HMAC(비밀키, `w:<회원식별자>:<ISO 주차>`)
- `month_key` = HMAC(비밀키, `m:<회원식별자>:<년월>`)

날이 바뀌면 `actor_key` 가 달라진다 — **일간 활성자 수는 정확하되 개인의 시계열은 원리적으로 만들 수 없다.** 주·월은 각각 그 기간 안에서만 이어진다. 리텐션·코호트는 이 설계의 의도된 포기다.

비로그인 방문자는 세 키가 모두 NULL 이다. 비밀키가 없으면 회원도 NULL 이 되어 횟수만 세인다 — 앱은 죽지 않는다.

## 왜 35일인가

월간 활성자 수는 그 달이 끝난 뒤 계산한다. 31일 달을 마지막 날에 집계하려면 원시 행이 31일치 남아 있어야 하고, 야간 작업 지연 하루를 더해 35일이다. **이보다 줄이면 월간 수치가 틀어진다.**

처음 제안한 30일은 이 계산을 놓친 값이었다(Dr. Ben 승인 후 구현 중 발견, 2026-09-20). 값 자체는 `USAGE_RETENTION_DAYS` 로 조정 가능하다.

## 제외 대상

`/proposals` · `/proposal-lookup` · `/my-proposals` 는 **조회 자체를 기록하지 않는다.** 익명 제출 직전의 페이지 조회가 남으면 3단계에서 끊어 놓은 제안과 계정의 연결이 여기서 다시 생긴다. 판정은 서버(`src/lib/usage/events.ts`)가 하며 클라이언트를 믿지 않는다.

`/admin` 은 운영자 본인 동선이라 신호가 아니고, `/api`·자산 경로는 사람의 화면 이동이 아니라 제외한다.

## 권한

읽기·쓰기 모두 서비스 롤(서버)만. `anon`/`authenticated` 정책 없음. RLS 는 켜 두되 정책을 두지 않아 기본 거부가 된다 — `watch_items` 와 같은 방식.
